# Account operations and Amplify runtime

The retained account system now uses controlled operator provisioning, current account checks, and conditional DynamoDB transactions. These commands operate on the existing users/whitelist tables; they do not introduce a reporting database.

## Runtime configuration

For an Amplify production build, configure:

| Setting | Value |
| --- | --- |
| `AUTH_URL` | The application's canonical HTTPS origin, without a path/query. |
| `DYNAMODB_REGION` | Region containing both account tables. |
| `DYNAMODB_USERS_TABLE` | Existing table with string partition key `id`. |
| `DYNAMODB_WHITELIST_TABLE` | Existing table with string partition key `email`. |
| `DASHBOARD_AUTH_SECRET_ARN` | Secrets Manager ARN for the signing key. |
| `DASHBOARD_TEMP_PASSWORD_HOURS` | Optional integer from 1 through 168; default 24. Applies to future temporary credentials. |

The signing key is a random secret of at least 32 characters. Secrets Manager `SecretString` accepts either raw text or a JSON object with an `authSecret` property. Only that recognized envelope selects a property; otherwise the entire value is validated as raw text, including raw text beginning with `{`. Invalid envelope values fail rather than falling back to the whole JSON string. The app never writes that value or AWS credentials into build configuration. Non-secret configuration files finish with mode `0644`; private operator credential files remain `0600`. Only the non-secret allowlist above is serialized to `.dashboard-runtime.json`, traced by Next, and copied to `.next/server/dashboard-runtime.json`. The runtime accepts the packaged server file when no root file or build environment exists. An explicit `DYNAMODB_REGION` override takes precedence; the hosting platform's default `AWS_REGION` does not replace a packaged table region.

Managed builds require explicit `DYNAMODB_REGION`; the hosting region is not a substitute. An unconfigured local production build can compile without inventing a region, but runtime account operations require a valid target. Managed builds fail when required configuration is missing or invalid. A direct local production run can instead supply a strong `AUTH_SECRET` at runtime; managed deployments use the ARN. Preview uses its fixed synthetic accounts and never reads account storage or Secrets Manager.

Attach an Amplify **SSR compute role** scoped to these two tables and the signing-key resource. The app uses the SDK's credential provider chain; no static AWS access keys are packaged. Required DynamoDB permissions are `GetItem`, `Scan`, `PutItem`, `UpdateItem`, and `ConditionCheckItem`; writes can be constrained to transactional operations. DynamoDB authorizes transactions through the underlying item permissions. Secrets Manager requires `GetSecretValue`, plus appropriate KMS permission if a customer-managed key is used. [AWS transaction permissions](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis-iam.html), [Amplify compute roles](https://docs.aws.amazon.com/amplify/latest/userguide/amplify-SSR-compute-role.html)

Signing keys are cached for at most 60 seconds during normal clock operation; concurrent reads coalesce. Failed refreshes do not use an expired key. Each signing-key load has a five-second overall deadline, including its response body. A timeout aborts the request and releases waiting callers; late results cannot replace the cache. Rotate a signing key as a planned operation that signs users out, allowing the cache interval during rollout. Validated runtime settings are captured once per process; restart to change them. Permission/account state is **not** cached across requests. Service clients use a one-second connection timeout, a three-second request timeout, a three-second response-inactivity timeout, and two SDK attempts; known transaction-conflict reads have at most three application attempts within a shared five-second deadline. These are operational defaults, not measured production latency promises.

## First administrator

Public `/auth/setup`, `/api/auth/setup`, and its status endpoint no longer create or expose account state. An operator with authorized AWS credentials provisions the first administrator:

```sh
npm run auth:operator -- bootstrap \
  --region us-east-2 \
  --users-table YOUR_USERS_TABLE \
  --whitelist-table YOUR_WHITELIST_TABLE \
  --email admin@example.com \
  --output /private/path/first-admin.credentials.json
```

Every command requires explicit region and table targets. Each invocation owns its own client/store and does not change web application configuration. Unrelated web-auth settings are not prerequisites for operator recovery. Passwords are generated by the command, never accepted as command-line arguments. The output must be a new `.credentials.json` file. Deterministic provisioning preflight runs first. The file is then created with mode `0600`, refuses overwrites/symlinks, and is synced **before** the conditional account mutation. A later race or uncertain result can still leave a prepared credential file; the file alone does not prove activation. Generated passwords are not printed. Keep the file outside the checkout, transfer the password privately to the intended person, and remove the file when no longer needed. Credential files are also gitignored as a precaution.

The initial user, email claim, and one-time initialization marker commit together. Ordinary provisioning also establishes this marker if it is absent, so it cannot race bootstrap past an earlier empty-table check. A concurrent bootstrap choosing another email cannot create a second initial administrator. Existing accounts block bootstrap. The administrator must sign in and choose a different password before accessing protected pages or admin APIs.

## Existing accounts and migration

Existing UUID account IDs, password hashes and explicit whitelist roles/active flags are preserved. Missing `authVersion` is read as zero. Pre-upgrade session cookies lack the version claim and require a fresh sign-in.

Stop serving the previous account-writing implementation before cutover. Run the migration against the chosen tables first without `--apply`:

```sh
npm run auth:operator -- migrate \
  --region us-east-2 --users-table YOUR_USERS_TABLE --whitelist-table YOUR_WHITELIST_TABLE
```

The preflight validates both complete account and whitelist populations, including whitelist-only entries, and detects duplicate/noncanonical email identities or conflicting links. Invalid records are reported by table/key/field without password hashes. Documented string and numeric `addedAt` values are accepted. `requiresCredentialReissue` identifies expired temporary credentials and legacy temporary credentials without an expiry. It does not guess which duplicate identity belongs to a person. Add `--apply` to create the conditional `whitelist.userId` links. A validation failure performs no writes. Apply is a sequence of conditional transactions, not one global transaction. A conflict/interruption reports completed and pending account IDs; fix the cause and rerun rather than guessing whether a write committed. The migration can be repeated after interruption; it does not change passwords, activate disabled users, or activate accounts with no whitelist entry. Explicit existing whitelist roles are retained; missing roles are filled from the account record.

Sign-in uses two point reads and one password verification for ordinary active, disabled and missing identities. It requires migrated email links; it never scans the user table. Management and migration retain complete, strongly consistent, duplicate-detecting legacy discovery. These controls reduce storage-work distinctions without claiming constant-time network behavior. Session checks use a transactional snapshot of the account and whitelist entry. No new tables or secondary indexes are required. Do not mix earlier nontransactional writers with this version or bypass the commands for access/password changes.

## Recovery and account administration

All examples below also require the same `--region`, `--users-table`, and `--whitelist-table` flags:

| Command | Additional arguments | Behavior |
| --- | --- | --- |
| `inspect` | `--email EMAIL` | Read-only identity, role, active state, revision and password-change status. No password/hash output. |
| `create` | `--email EMAIL --role viewer\|user\|admin --output FILE.credentials.json` | Controlled provisioning, including recovery if no administrator can sign in. Refuses duplicate email claims. |
| `reset-password` | `--email EMAIL --output FILE.credentials.json` | Generates a new temporary password, increments the revision, and requires a different password on next sign-in. |
| `set-access` | `--email EMAIL --role viewer\|user\|admin --active true\|false` | Changes account and whitelist access together and increments the revision. |

A lost response is not proof that an operation failed to commit. The private credential file remains available. After uncertain creation, use `inspect` and compare its account ID with the file. After an uncertain reset, a new reset with a fresh output file establishes a confirmed credential. Do not reuse an existing output file or blindly overwrite an account.

Normal administrators can use the protected admin screen and create/reset APIs. The account list and operator inspection show effective access; unprovisioned, inactive, and unlinked entries are distinguished and cannot be reissued through the list. The screen displays a temporary password and its expiry for private delivery, confirms accidental dismissal, and offers Reissue password. Clipboard failures stay visible inside the dialog; list-loading failures are not shown as an empty successful list. Reissue replaces the existing password immediately, including when that password was permanent. Self-reset also invalidates the administrator's current session, so a lost self-reset response may require another administrator or the operator recovery command. Normal administrators can continue using the protected create/reset APIs. These operations include current-admin conditions in the same transaction as their writes. A changed version, disabled whitelist, downgraded role, or mismatched identity blocks a write even if the request passed its earlier session check. Self-resets avoid targeting one item twice in a transaction. Password/access changes invalidate prior sessions on their next server request; already-rendered browser content is not remotely erased.

## Verification

`npm run check:all` includes unit/component checks, real DynamoDB Local transaction tests, both builds, a copied-production-artifact HTTP smoke test, Storybook and Chromium/WebKit checks. Java 17+ is needed for the emulator; CI installs Java 21. AWS's DynamoDB Local **3.3.2** archive is pinned by immutable object version and SHA-256. It is downloaded into the ignored development cache; no emulator is shipped with the application. Test tables are in memory with synthetic credentials and isolated ports.

The production fixtures copy the built artifact and public assets without source or `.env`, loads packaged configuration, uses a signed SDK request against a controlled secret-service fixture and a real local DynamoDB endpoint, and verify login, legacy whitelist metadata, account creation, reset, required password change, anonymous payload exclusion, storage-outage recovery, and session invalidation. Chromium and WebKit exercise the real admin/reissue/password-change UI and subsequent protected navigation. It does not validate a live IAM policy, Amplify deployment, or edge abuse controls. Those are environment acceptance checks; the implementation mechanisms and offline failure paths are executable in the repository.

## Account mutation request contract

Cookie-authenticated account changes require an `Origin` matching the configured `AUTH_URL` and `Content-Type: application/json`. Browser fetch calls supply the origin automatically. Direct local production and non-browser cookie clients must also use the canonical configured origin. Missing/opaque/untrusted origins and simple content types are rejected; no origin is inferred from caller-supplied host/proxy headers. Auth.js endpoints retain their own CSRF-token protocol.

The server store captures one client and target at initialization; restart the server to change its account target. Current account/permission data is still read on requests. Operator commands instead bind a fresh owned client to each explicit invocation and close it afterward.

## Temporary credential lifetime

Set `DASHBOARD_TEMP_PASSWORD_HOURS` in the web deployment and in an operator command's environment. The default is 24 hours; the accepted range is 1–168 integer hours. An explicit empty or invalid value is rejected. For example, use `DASHBOARD_TEMP_PASSWORD_HOURS=48 npm run auth:operator -- ...` with the documented command and explicit targets. Restart/deploy the web process after changing its configuration; its account-store instance captures its policy at initialization.

Each issuance stores an exact UTC expiration, returned in the API response and private operator file. Configuration changes affect future issuance only. At `now >= expiresAt`, the temporary credential is invalid; the administrator/operator must reissue it. Permanent passwords do not expire under this policy. A required password change removes temporary expiry and increments the account revision. No DynamoDB TTL deletion is used.

Create/reset operations use the same prepared credential in the file and transaction. A file-write failure prevents the operator mutation. Concurrent resets prepared against the same revision cannot both commit. A lost HTTP response may still represent a committed reset; reissue deliberately rather than retrying an unknown credential automatically.

## Ordered deployment and rollback

For the transition from the currently deployed dashboard, use this controlled account cutover procedure where applicable to that deployed version. The [approved 2026-10-29 delivery sequence](../product/README.md#approved-delivery-sequence) places the reviewed frontend deployment before real reporting integration. The live site has no current users and temporary downtime or frontend defects during transition are acceptable. This release uses clearly labeled sample reports with production authentication. Continued availability of the old reporting site is not a release prerequisite; account-data integrity, authentication and access checks remain prerequisites. Confirm the actual production branch settings before any merge to a production-tracked branch; a repository webhook alone does not establish its auto-build behavior.

This procedure is the account/hosting acceptance checkpoint, not the reporting-database integration procedure. Complete hosted sign-in/access acceptance first; then introduce real reporting sources one area at a time under the [reporting acceptance checks](acceptance-matrix.md#delivery-milestone-acceptance). A missing reporting source does not require a different authentication mode.

1. Identify the actual Amplify app, production branch, auto-build/preview settings and last deployed revision. Pause automatic production builds before merging if a merge would start deployment. Do not grant public PR previews the production compute role.
2. Prepare recovery: confirm an authorized operator can target the account tables, preserve a recoverable table backup and the prior deployable artifact/configuration, and record the existing key/role dependencies. Do not retire old credentials yet.
3. Provision the signing secret and least-privilege branch-scoped SSR compute role; configure canonical origin, explicit account region/table names, secret ARN, and intended temporary lifetime. Verify shared hosting-level login throttling and trusted client-address handling. An in-process counter is not an equivalent control.
4. Run the new operator preflight without `--apply`. Resolve all reported invalid/ambiguous records and plan reissue for `requiresCredentialReissue`. Do not auto-normalize identity keys or guess duplicate ownership.
5. Enter the approved maintenance window and stop the old account-writing app/other writers. Rerun preflight immediately before the transition; separate scans are not a multi-table snapshot.
6. Deploy the new artifact in a controlled state. Verify packaged-file readability and runtime configuration, then `/api/auth/csrf`. Existing accounts must be linked by the next step before sign-in acceptance. `/api/health` alone proves neither IAM nor authentication readiness.
7. Apply account-link migration with the explicit target before reopening sign-in. Normal sign-in uses bounded point reads; legacy discovery scans remain in operator/management paths. If interrupted, inspect the completed/pending receipt and rerun safely. Reissue affected temporary credentials privately. Verify expected admin permissions after migration, creation/reset/change-password, revocation, and anonymous HTML/RSC exclusion.
8. After acceptance, reopen access and restore the intended build policy. Retire legacy `S3_*`/`NEXTAUTH_SECRET` settings and IAM keys only after reviewing rollback dependencies. The prior build embedded legacy credentials; reverting code is insufficient once those credentials are disabled. Record that point as the rollback boundary.

If acceptance fails, keep maintenance active. Choose either an explicitly compatible rollback or forward repair with the operator; do not run old nontransactional writers concurrently with the new implementation. Record cloud acceptance separately from local and hosted CI results.
