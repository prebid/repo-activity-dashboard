# Foundation contracts

These contracts apply to the current sample-backed frontend. The [approved delivery sequence](../product/README.md#approved-delivery-sequence) governs remaining frontend work, early hosted release, real reporting integration and deferred features.

## Composition and imports

Protected pages call the current-viewer guard directly or through guarded sample loaders before creating their views. Layouts provide the authenticated shell but are not the sole access gate. Routes compose current account context, prepared sample values, and feature views. Feature views receive typed display models. Shared components must not know which repository, account store, GitHub collector, or report calculation produced a value.

`dependency-cruiser.config.mjs` resolves TypeScript aliases, relative imports, re-exports, and statically resolvable dependencies. It rejects source cycles, unresolved imports, shared-component dependencies on features, cross-feature imports, reversed pure-layer dependencies, and presentation paths (including AST-discovered `use client` entry points under routes) that reach server/auth/AWS/sample modules or Node builtins. Package internals under node_modules are not traversed; this is a source architecture check, not a dependency security audit.

Application imports cannot reach operator command scripts. Only the HTTP auth adapter and internal session transport may import raw Auth.js handlers; shared tables cannot reach Next routing. Account store instances bind one client and immutable target; the server adapter owns its default instance, while operator invocations own separate clients without changing process-wide table settings.

The separate retirement checker rejects exact known retired reporting paths, packages in either dependency section, obsolete scripts, raw-store strings, and computed module imports. Dependency-cruiser is the single owner of source import-layer rules; ordinary nested directories named services, store or validation are allowed. Its AST scan covers application JS/TS source extensions, including JSX/TSX and CJS/ESM variants. Runtime-generated code, arbitrary HTTP destinations, and third-party package internals are outside that check. Both checkers reject empty input. Positive and negative fixtures exercise the actual checkers.

## Table state ownership

- The URL owns search, sort direction, sort key and page, written by the one URL codec (`src/lib/presentation/url/`): a parameter registry per report route and screen, a canonical serializer and the frozen v1 defaults (`url-defaults-v1.json`). An address records only fields that differ from the v1 defaults. A list is one comma-joined field with literal `,` `:` `@`, except the free-text `labels` and `branches`, which repeat their key; a descending sort is `-column`; column visibility is a `cols` diff against the table's v1 columns (`id` shows, `-id` hides); the Timeline is the bare flag `?timeline`. An unknown parameter or a malformed value renders the screen's invalid view. A link in the pre-codec form is decoded by the frozen readers in `url/legacy/` and answered with a 307 to its canonical form; exports accept it without a redirect. A Timeline supporting view keeps its records table in `dq`/`dsort`/`dpage`/`dcols` and an author's authors list in `listq`/`listsort`/`listpage`.
- A saved sort, read on the server from the viewer's preference cookie (see Preference cookies), applies only to an entry: a report address holding only view selectors (`timeline`, `view`, `lens`, `sample`, `gap`) and return context (`back`), without `v`. Every other address shows the v1 default for an absent field. A well-formed saved sort on a column this table lacks does not apply here and stays saved for the tables that have it. An invalid section or a refused cookie write must not block interaction. Saved preferences live in this browser's cookies; they are not server-stored account settings.
- Shared-table column visibility defaults to component state; All Repositories supplies controlled, account-scoped saved column choices. Export errors remain temporary component state. Search/sort changes reset the page. Pages contain at most 50 rows.
- The shared table consumes a controlled query and callbacks. Application controllers observe Next search parameters and write history only through the codec hook (`src/lib/navigation/use-url-state.ts`). A write, and a server navigation to the same page (route and screen), keeps `location.hash` unless its href names a fragment, and records in `history.state` the address an in-app push came from (`dashboardPrevious`); Next keeps its own router metadata beside it. Search has a local draft and a 250 ms debounce. Enter, filter activation, same-tab internal links, sorting, and export capture the latest intended query; blur alone leaves the debounce in control so shrinking results cannot move a pointer target mid-click; query/history and scope changes cancel pending writes. Browser back/forward and same-route links update the table. Ascending direction is the default and is omitted from URL writes; flushing an untouched query leaves history unchanged.
- Saved sorts reach a page through its entry's 307 or through the links that open it, which carry them as explicit fields (decision C3), so hydration changes nothing. A rendered bare entry is pinned to its explicit form, `v=1`, before its first in-app navigation (a fragment link within the page is none), so Back never opens a later saved view. Invalid pages, including a Timeline page past the last one, are reconciled against matching totals in memory, without history writes. A saved preference is bound to the account ID and authentication revision and keyed by view kind and table kind, not by repository or sample. Storybook and local component tests use a router-independent memory controller.
- The dashboard's structural `main` landmark remains stable. Its page contents are keyed by account ID and credential revision, preserving drafts across a same-identity refresh and clearing mounted page state when either identity value changes.

For local samples, `rows` is the complete supplied population; search/sort precede pagination and export includes every matching row and the selected columns, with required identity/context metadata.

The current table has one mode: a complete supplied sample population. Remote table paging is deferred until there is a real adapter. Contribution CSV downloads use an authenticated, read-only prepared-sample endpoint; both supported layouts share the same builder. Catalog states use the actual shared route error component and real pending controls, rather than inventing feature-specific loading screens.

The table accepts optional grouped column metadata, widths/alignment, a pinned identity column, and controlled visibility. Its local visibility remains the fallback for existing callers; there is one visibility owner. Group and leaf headings are associated with cells, overflow is announced only when measured, and scroll containers are keyboard accessible. Feature views own metric meanings and default column sets. Optional `sortValue` supplies a ranking key without replacing the actual `value` used for displayed/exported data; this keeps repository comparison groups together without duplicating the first period’s numbers. A bounded page-size option allows 48-row pages for three-row groups while retaining the shared 50-row maximum. All Repositories uses separate backlog/activity query and sort-preference scopes. Peer-table query changes do not discard a pending search. Page-scope controls capture both tables before navigation; discrete repository/period/aging choices push explicit URL snapshots so Back/Forward does not depend on newer saved defaults.

## All Repositories settings

All Repositories has no table-local search. The searchable repository picker controls the included rows; legacy `backlog.q`/`activity.q` values cannot filter them and are dropped on scope updates or Reset. Search remains available on other record/report tables. Repository selection applies to both tables; the timeframe changes activity only, and aging selects which cumulative age columns are visible; selecting none hides the PR age group. Period Activity accepts one or two independently selected presets/custom ranges. Each repository group contains the first period, the second period, and an automatic Difference row (Period 1 minus Period 2). Its visible repository name appears once, while every row retains an accessible identity; period labels replace repeated numbered badges. The compact difference row separates groups and uses neutral signed values, or a dash if either operand is missing or partial. Period and difference rows are distinct display-model variants, so a derived difference cannot masquerade as a record-count cohort. A separate sort accessor keeps each group together and ranks numeric columns by Period 1. Swap periods changes the ranking period and difference direction. Custom range actions are separate from preset dropdowns, and there is no Show change control. The guarded server loader supplies a compact sample collection with one current backlog and the prepared period values; pure presentation helpers select display values without requests, historical calculations, or a reporting database.

An explicit address field is never replaced by a saved value; saved settings apply only to the bare entry. Repositories are one comma-separated `repo` field of catalog slugs in catalog order, left out for every repository (`repo=prebidjs,prebidserver`); aging choices are one ascending `age` list (`age=30,60`, default `30`). A present empty value means no selection. An unknown repository, period or age renders the invalid view; an old link with repeated `repo` IDs or `age` fields is answered with a 307 to this form. Relative presets are saved as presets, not resolved dates. A period is a preset ID or `YYYY-MM-DD..YYYY-MM-DD`; Period 2 uses its own `period2` field. Invalid or duplicate second periods fall back to the valid first period with a visible notice. Unsupported custom ranges show missing sample values while retaining backlog.

One versioned preference section, `overview` in the repositories cookie, owns repository IDs, ordered periods/custom dates, selected aging thresholds, and each table's other visible columns. Age visibility is derived from the threshold selection, not duplicated in the other-column list. The dedicated PR age selector edits that value. The general Columns menu exposes only the other backlog columns, while the shared table still renders and sorts all selected columns. Version 3 reads version 1 and 2 settings by carrying over the previous period as Period 1 and preserving aging/other column preferences. Retired Show change flags are discarded. Version 1 visible aging thresholds become a one-item selection; a previously hidden age column becomes an empty selection. The existing two table controllers own their sort sections, `overview.backlog.sort` and `overview.activity.sort`. A bare `/repos` is the Summary's entry: when the saved settings or sorts differ from the v1 defaults, the page answers with a 307 to the saved explicit form, so the page renders once and writes no history. The masthead link, and the "All repositories" crumb of a page that names no Summary, carry that explicit form after hydration, so an ordinary click needs no redirect. A deliberate change saves only the fields it changed, merged into the section the cookie holds, so a setting an explicit link shows but the viewer did not change is not saved. An invalid `overview` section renders the defaults with "Saved All repositories preferences are invalid. Defaults are shown." and is deleted after hydration while the cookie still holds it. A refused cookie write keeps the controls usable for the current visit, and the toolbar says that changes still work in the URL. Reset view clears only these three sections and this report's URL fields, preserving theme and other reports. Before pushing a new scope or resetting, the controller pins a bare entry to `v=1`, so Back restores the view it showed. Column visibility remains a saved display preference rather than URL/history state. No cross-device preference synchronization is implemented.

## Runtime account boundaries

Account request bodies, consumed API responses, and loaded account/whitelist records are validated with Zod. The HTTP boundary limits actual body bytes to 16 KiB and body reads to five seconds before parsing; absent/misleading Content-Length does not bypass counting. Login/current-password verification accepts at most 1 KiB of UTF-8 input, without trimming or truncation. Oversize and timed-out bodies return 413 and 408 respectively. Invalid user input returns 400; malformed store responses and store failures remain failures. Production credential validation checks whitelist membership, account existence, and password verification and returns only safe identity fields.

Client mutation handling distinguishes a parsed 4xx rejection from an uncertain network, malformed-response or server-error outcome. Uncertain outcomes receive operation-specific recovery guidance rather than raw transport messages or an automatic mutation retry. Server-page retry refreshes the router before clearing its error boundary.

Account JSON responses, including errors and temporary credentials, use `accountJson` to enforce `Cache-Control: private, no-store`. Admin list fetches also request no-store. Auth.js protocol responses retain library handling; the current-session adapter preserves cookie semantics while applying the account response policy.

Custom cookie-authenticated account mutations require the canonical configured origin and JSON content type. Their policy is shared by the create/reset/change-password routes. Auth.js endpoints keep their existing CSRF protocol.

Account mutations reject preview builds before invoking real authentication/storage. Admin mutations also require an administrator and completion of mandatory password changes. Password change acts on the authenticated identity, never a user ID supplied in the body. API checks are independent of page-layout checks. Generic credential failures perform password-hash work even for unknown/disallowed accounts; this reduces one timing distinction but is not a constant-time or deployed throttling guarantee.

Production Auth.js handler tests use real CSRF/session-cookie processing with controlled dependencies. Every protected server use resolves current account/whitelist state and its revision. Auth.js owns token verification, CSRF, cookie chunking, expiry and renewal. The configured session lifetime remains 30 days. Normal page reads do not deliver renewed cookies, and the UI does not poll for renewal; a successful explicit session-endpoint request can renew the cookie. This is not an enforced absolute 30-day cap. Tokens carry identity/revision and standard library claims; profiles and roles are projected from current storage. The public session response is withheld until current-account resolution succeeds. Revocation returns a null session without renewal; storage outages return 503 without deleting or renewing the incoming cookie. Corrupt account/configuration data returns a safe 500. Failed lookups log allowlisted diagnostic categories/codes, never raw records or exception messages. Known transient read conflicts have bounded retries and a shared five-second deadline. Effective privilege is bounded by both current roles. Password/access changes increment the revision; admin mutations also verify current actor conditions in the write transaction. Secret values remain server-only and are loaded through the configured runtime provider. Viewer memoization is request/render scoped. Already-delivered browser data is not remotely erased by revocation; new reads/writes revalidate. Explicit auth transitions refresh router state and notify other open tabs without a global SessionProvider or session polling.

Password forms own an abortable operation for their mounted identity. Disposing the form prevents a delayed password response from starting automatic sign-in or navigation. Once a password write is confirmed, fields clear and subsequent sign-in failure goes to a refreshed recovery login with a new-password notice. Cancellation cannot undo committed server work or cancel an Auth.js request already sent.

User creation reserves the normalized email and writes the user in one conditional transaction. A separate bootstrap marker prevents concurrent first administrators across different email addresses. Legacy numeric/string whitelist timestamps are accepted. Preflight scans both full populations, including whitelist-only records. Validation failures cause zero migration writes; interrupted apply reports completed/pending work and is safely repeatable. Legacy links are added by conditional operator migration; existing UUIDs/password hashes and explicit active/role states are preserved. Public setup is closed. Operator-created temporary credentials are synced to a new private file before mutation, and the first password must be different. One prepared operation supplies the password/hash, expiry and target revision to web and operator flows. Expiry is checked during sign-in, current-viewer resolution and password changes. Reissue invalidates the previous credential; a permanent-password change removes temporary expiry. Legacy temporary credentials without expiry require reissue. The admin dialog supports private copying, deliberate dismissal and reissue; no password-bearing mailto links remain.

The [account operations guide](account-operations.md) records the implemented commands, configuration, migration, recovery and deployment assumptions. A built-production HTTP test exercises the packaged server with a real local DynamoDB service and a controlled Secrets Manager HTTP fixture. It does not certify a live AWS IAM policy or Amplify environment.

## Verification policy

`npm run check` runs formatting, type-aware lint, strict app/test/tool typechecking, both architecture/removal checks, and unit/component tests with coverage. `npm run check:all` additionally runs a full dependency audit, real local account transactions, a production-auth build and packaged-server HTTP test, a preview build, Storybook, and Chromium/WebKit browser tests. CI distributes those same gates across required jobs: fast checks, one build/packaged-production stage, isolated browser shards, and a final `quality` gate that checks source identity and complete test-case coverage. No tests, coverage thresholds or browser engines are removed; `tests/unit/quality-workflow.test.ts` fails when the workflow steps diverge from `check:all` or `test:e2e`, and `npm run check:all` remains the complete local command.

Coverage includes all application TS/TSX, excluding declarations. Thresholds are per file within explicitly listed critical groups: presentation helpers, table/query state, credential/access/request policies and auth wiring, admin/password API handlers, the server Timeline loaders (`src/server/timeline-*`), the shared navigation, CSV download and Timeline table/value/support-frame components, and the Timeline chart. Feature views and screens have no per-file floor; component and browser tests cover them. The report also exposes uncovered scaffolds, retained admin screens, UI primitives, and store mutations. There is no claim of whole-application coverage or a blanket percentage that conceals those gaps. Browser execution is reported separately from unit coverage.

Required suites must select tests and report no failures/skips. Full test commands clear prior reports and enforce individual outcomes/counts with `scripts/check-test-results.mjs`; focused-only suites are prohibited by runner configuration. Browser assertions cover actual values, URL behavior, keyboard/theme/style behavior, export bytes, and preview restrictions; screenshots are inspection artifacts, not approved design baselines. Offline storage tests do not claim a live service integration. Same-author verification does not replace independent review.

New-password rules are shared between forms and server validation: at least six Unicode code points, no character-class requirements, and the 72-byte bcrypt limit. This preserves the current login policy. Existing credential verification is retained; this does not migrate previously truncated passwords. CSV prefix escaping covers the recorded string cases but is not a guarantee across every spreadsheet importer or re-save operation.

The root theme provider preserves the current site's Dark default and `dashboard-theme` saved preference. The merged [authentication design](../product/login.md) provides the approved branded login, password setup, and sign-in-error screens. Reporting-page layouts follow the [All Repositories implementation plan](all-repositories-plan.md). The legacy live-report views, private report bundle, preparation scripts and verification workflow are retired along with the original reporting layer.

## Deployment acceptance

The approved 2026-10-29 sequence deploys the reviewed frontend before real reporting integration: the current live site has no users, and temporary downtime or frontend defects during transition are acceptable. Real reporting integration is not a prerequisite for hosting the reviewed frontend; sample data must remain clearly identified. Production builds retain real account authentication, never the local preview identities. A separate staging site is optional; hosted validation can precede incremental database integration on the internal site.

Control Amplify automatic builds before merging into a production-tracked branch. Verify live Amplify file handling, branch deployment triggers, IAM/account configuration and shared login throttling before deployment. Use the account migration/recovery sequence in [account operations](account-operations.md) as applicable to the actual deployed version; do not run incompatible account writers together. Local and CI verification do not certify environment acceptance. Early deployment does not certify real-data correctness or authorize deployment by itself. After hosted acceptance, follow the incremental reporting-integration checks in the [acceptance matrix](acceptance-matrix.md#delivery-milestone-acceptance). Introduce a real adapter and bounded retrieval/export behavior with their first consumer; retain the reviewed view contracts and deterministic sample mode.

## What visually locked means

Before the new reporting/data layer begins, review and record the following for each page in the initial frontend scope. Custom groups are deferred until after real database integration and receive their own visual review later:

- Navigation, content hierarchy, component placement, spacing, typography, and supported theme behavior.
- Default and optional columns, widths, numeric formatting, sorting, filters, table density, and narrow-screen/overflow behavior.
- Click destinations, URL/filter context, paging, saved preference behavior, and export interactions where applicable.
- Normal, busy, empty, loading, error, partial-data, known-zero, and missing-value states, including long names/titles and large numbers.
- Repository graph types, labels, scope, and textual alternatives; table-only contribution and tracking reports.
- Representative screenshots at agreed viewport sizes and interaction checks that establish the reviewed baseline.

Visual values come from the design tokens. Colours, shadows, radii, font families and font sizes are defined once, as custom properties in the top-level `:root` and `.dark` rules of `src/styles/prebid.css`, and mapped for Tailwind in `src/app/globals.css`; every other stylesheet, class string and style object reaches them through `var(--prebid-*)` or the mapped utilities. `scripts/check-design-tokens.mjs`, run by `npm run check:boundaries`, enforces this over CSS and TS under `src/` and TSX under `src/` and `.storybook/`: it fails a colour, shadow, radius, font-family or font-size literal outside those token rules, a `--prebid-*` reference that `prebid.css` does not define, a typed text arrow (U+2190–U+21FF) in `src/`, and feature CSS that restyles a native control through a descendant selector. Remaining exceptions are entries in `scripts/design-token-allowlist.json`, each with the redesign phase that removes it and a reason; an unused entry or one owned by a completed phase fails. Values the scanner cannot read statically are listed and may not exceed a pinned count.

User review establishes the visual baseline; screenshots do not approve themselves. Repeat those checks during integration. The goal is to preserve the agreed frontend while replacing its data source. Mocks cannot prove real-data completeness or performance, so any integration-discovered mismatch must be identified and resolved explicitly rather than silently changing a screen's meaning.


## Dependency maintenance

The selected stack remains Next.js, React, TypeScript, Tailwind v4, Radix and Recharts with Amplify hosting. Next.js 15 remains the selected Amplify-compatible major. ESLint 9 and Auth.js v5 beta are deliberate compatibility holds; upgrade those lines only with compatible integration evidence. Pins and normal dependency auditing remain part of the quality checks.

### PR and issue drilldowns

Summary links use the typed repository drilldown builder and the receiving route uses its matching parser after the current-viewer guard. Record lists preserve current/period scope, the selected row's UTC range, primary branch for merges, and age threshold. A validated `/repos` return URL captures both summary table queries and scope settings. Unknown repositories remain 404s; malformed filters never fall back to an unfiltered cohort. Missing/partial sample coverage is separate from known empty results. Shared table pagination/search/sort operates on the complete supplied sample list, while the overview receives only compact prepared summaries. The PR/issue list view has no sample, router, auth, or database imports. Author, contribution, and duration destinations use the same validated route and shared feature-level frame. Unique-author rows remain compact and link to guarded, author-filtered PR/issue lists with independent pagination/search/sort and parent author-list state; contribution rows retain their account/PR/type identity and first-credit time; duration details retain both the median measurement and merged-PR sample size. These units are never substituted for each other. The shared table remains unaware of reporting semantics.

Author-specific record routes require the existing viewer guard, a catalog repository, a valid account handle, and a period-scoped PR/issue author metric. The parent author-list URL is rebuilt from those validated fields and its allowed `authors.*` table state; it is not an arbitrary redirect. Child PR/issue query fields do not overwrite the parent state. Author overview models carry identity and counts only, while the selected author's complete fake population is supplied to the shared 50-row table. Column `cell` values are pure render callbacks; stateful cell UI is returned as a component element so callback changes do not remount it.


## Reporting column help and profile navigation

Shared reporting tables obtain explanations from `DataColumn.description`: native header hover and accessible descriptions are backed by the same metadata as the visible-column help dialog. The help control lives beside the table title and does not sort. Individual feature pages do not add a separate competing definition disclosure. Explicit CSV column definitions do not enter the display/search index. All enabled table exports use one shared Export CSV dialog, default to visible columns and include all matching rows. Export-only coverage fields follow their selected metric; identity/context metadata remains automatic. Alternate layouts are provided by the owning feature through the same dialog. Other file formats are deferred until after custom groups and core milestones.

Account profiles and dashboard reports have distinct destinations. Profile components validate HTTPS GitHub/sample URLs, expose the visible name/handle in their accessible name, and open externally. Sample accounts use reserved placeholder URLs. Contributor display names open internal reports with selection/return context; their @handles open GitHub profiles. Human, agent and bot icons remain beside identities and on the Account type choices, and Account type is its own default column/filter. Period, repository, population, zero-total visibility and export controls are implemented with prepared samples.

Optional comments and final merged-diff volumes are separate from lifetime-once contribution credits. Their definitions and merge-period attribution are maintained in the [contribution contract](../product/contributors.md#optional-comment-and-merged-change-volume-columns). These are prepared facts/display projections, not a reinstated reporting collector or database API.


## Contribution report boundaries

Contribution report inputs are validated into owned, deeply frozen snapshots. Only those snapshots may reuse their private sparse index; mutable caller inputs are parsed into a fresh snapshot. Credits, comments, final-diff assignments and coverage overrides are indexed once by account/repository/metric. Aggregation uses explicit cells plus the shared zero/null coverage baseline, preserving known-zero, partial, missing and not-applicable semantics without walking the full account × repository × metric product. Identity and volume validation use indexed relationships rather than nested record searches.

Overview eligibility is indexed separately, before applying global coverage defaults: positive recorded values, record-specific partial/missing values or an explicit account/repository partial/missing override qualify the account. Complete zero and not-applicable values alone do not. Global gaps cannot create rows for unrelated directory accounts. Companies qualify through at least one eligible selected member, but company totals and member counts still include all selected members. Tab counts and both export layouts use the same eligible population, independently of visible/exported columns. Eligibility depends on the lens: each indexed cell keeps any-metric evidence and Reviewer-role evidence (positive, partial or missing in Reviewer contributions, Approval contributions or Merges performed, self-merges included). The Contributors lens uses the first; a Reviewers-lens overview uses the second, and its `all` flag ("Show all N accounts" / "Show all N companies") switches back to the first. The report carries both population counts for the switch label, and overview CSVs record the lens and the listed population in their context columns. Global totals retain the full selected scope and its uncertainty. Focused member rosters and repository breakdowns retain their existing coverage behavior. The `coverage-gap` sample combines 251 contributing accounts with 3,000 directory-only accounts, partial reviewer history and unavailable optional metrics.

Report payloads contain common summary/context metadata and one discriminated active table. Overview tab counts and focused company member counts are numbers; unused collections and expanded included-account ID lists are not sent. Supporting-record views carry no hidden report table or merged-diff objects. Table query contracts and the 50-row limit live in the model layer; the architecture guard also rejects type-only model imports from presentation/navigation.

The account/company picker uses the authenticated, read-only `POST /api/reporting/contribution-options` endpoint. It serves prepared identity labels in pages of at most 50, or validates saved identity references; it does not collect reporting data, query a database, or persist settings. Responses are private/no-store, requests are bounded, and stale, canceled, timed-out or malformed responses cannot replace current choices. Draft selections survive paging, searching and retries. Saved report scopes with identity references are validated against the directory on the server when a report or Timeline entry renders, so no in-app code calls the validate action; explicit report URLs still validate identities on the main server boundary. Normal report responses carry the repository controls only, not the account/company catalogue.

Reproduce selector/serialization measurements with `node --import tsx scripts/measure-contribution-reporting.ts`. Timings are diagnostics, not machine-dependent CI thresholds. Tests assert unchanged metric answers, bounded identity payloads, immutable ownership, and stable report size when inactive catalogue entries grow. Fake populations remain complete for table filtering/export before 50-row display pagination; this does not introduce an unused remote-table adapter.

## Contribution navigation and preferences

Explicit contribution URLs and default reports render their rows on the server. Saved preferences are read from the contributions cookie on the server, so they do not gate the report's initial markup and the first render is final. React-only table controls and every report toolbar (its filters, settings and resets) remain disabled until the existing client-ready boundary attaches their handlers; rows and ordinary links remain server-rendered. A delayed-JavaScript browser regression verifies that early input cannot be lost. The Contributors and Reviewers navigation links render bare on the server and, after hydration, carry a saved scope that can be checked from the enabled repository catalog and preset definitions, plus their own lens's saved table presentation; only their hrefs change. The masthead reads the lens from the address on the client (`useSearchParams` in `DashboardHeader`), so the server render and client navigations both mark the active lens. They read the cookie again after a save in its window and when the window regains focus or becomes visible, because cookies fire no cross-tab event. A report address holding only view selectors is an entry: when the saved scope (on `/contributors`, `/reviewers` and `/companies` only) or the shown table's saved presentation differs from the v1 defaults, the server answers with a 307 to the saved explicit form; a contributor or company page never takes the shared saved scope (decision C2). An entry at the defaults causes no redirect. The v1 contribution columns are the lens's set (decision C5): in the Contributors lens PRs authored, Authored PRs merged and Issues authored, sorted by Authored PRs merged; in the Reviewers lens Reviewer contributions, Approval contributions and Merges performed, sorted by Reviewer contributions. `/reviewers` is the Reviewers lens's people overview; other contribution routes carry `lens=reviewers`. `lens` on `/contributors` or `/reviewers` is not a registered spelling and renders the invalid view, and `all` is accepted only on a Reviewers-lens overview without a metric and on its exports. An invalid view takes its lens from the raw query, as the document title and the masthead do, so `/contributors?lens=reviewers` is the Reviewers invalid view, headed "Reviewers" and linking to `/reviewers`. A signed-out visit to `/reviewers` signs in to `/repos`, because `safeReturnPath` (`src/lib/presentation/navigation.ts`, frozen with authentication) does not list `/reviewers`; `/companies?lens=reviewers` and person or company pages with `lens=reviewers` keep their callback. Production rendering checks inspect real report markup and browser table rows, excluding serialized RSC scripts.

Report scope has one reader/writer, including account types. A deliberate filter change persists only that field (population changes include exclusions) into the `contributions.scope` section, using the scope the cookie holds at that moment as its baseline, so a field saved from another page or tab is kept. A repository narrowed by a supporting-record link is not saved when a user changes only the period. Explicit URLs remain authoritative and visiting a link does not save it.

Contribution column and sort preferences are sections of the contributions cookie keyed by lens and table kind: `contributions.<table>.columns` and `contributions.<table>.sort` in the Contributors lens, and `contributions.reviewers.<table>.columns` and `.sort` for the contributors, companies, members and repositories tables in the Reviewers lens. The supporting-records table (`contributions.details.*`), the report scope and `timeline-support.contribution.sort` are shared by both lenses. Sections are bound to the account and authentication revision; sample-scenario isolation is dropped. A column section is version 1 (`columns`, a map of choices) or version 2, with `hideZeroMembers` and, in the Reviewers lens, `showAllAccounts`. Version 2 stores columns that match a Column set other than the lens's own by the set's name (`set`), with a `cols` diff only for identity columns that differ from v1; any other choice is `cols`, the URL's column diff against the lens's v1 defaults (which are the lens's own set). Readers accept version 1 and both version 2 forms; a deliberate change to a non-details table writes version 2, and the one-time localStorage migration still copies version 1. A version 2 section is 47 bytes of JSON at the lens defaults and 49 for All columns, where a version 1 map of every column took about 1.2 KB; a Custom choice still names each column it changes, so every column but one shown takes about 800 bytes. The server checks each section's shape, and the client applies only the columns its table renders, so a choice for a column this table lacks is kept for the tables that have it. An invalid column or sort section renders the defaults and is deleted after hydration while the cookie still holds it. The former localStorage values are copied once into an absent section: the shared table key wins over the former entity key, and invalid values are not copied. The old keys are removed once copied, superseded by a cookie value or invalid, and kept when the cookie could not be written. Other reports' sections are untouched.

Return context travels as `back` frames (P5d). A frame records only how a parent differs from the parent derived from its child: `-` is the derived parent, `~pairs` a difference on the derived route, `/path~pairs` another route, and `!` an ancestor that cannot be restored. Values escape every UTF-8 byte outside `A-Z a-z 0-9 - . _ , : @` as `*HH`, so a frame never holds `%` and is never double-encoded. A link carries at most eight frames, nearest first; their `&back=` parameters take at most 1,000 characters and the whole href at most 7,500 bytes, and farther frames are dropped first. When a dropped frame is not `-`, the kept frames end with `!`, so that ancestor shows as unavailable rather than as its derived default; a link that cannot keep its parent frame and that mark is unavailable. The immediate parent is never partially reconstructed: when it cannot fit, the detail link is unavailable with the existing explanation, and an edit that would take a page's own address past 7,500 bytes is rejected without saving it. A child edit rewrites only its first frame, against its new derived parent, so the resolved parent never moves. An unresolvable frame shows that crumb and every farther one as unavailable ("The page this link came from is not available."), never a broader report; a tab whose frame is lost opens its derived target. A crumb whose target is the entry this page was pushed from goes back in history (`history.go(-1)`) instead of adding an entry. Old links with `returnTo`, `summary`, `timelineParent` or a version 1 or 2 base64 `nav` trail are decoded by a decode-only reader (`url/legacy/trail.ts`) and answered with a 307 to their frames; a trail key that decodes to nothing becomes `!`. Links no longer write those keys. This application budget is not certification of deployed Amplify/proxy limits.

## Composable column selection

Column visibility and CSV choices share one selection model and renderer. `selectionGroup` and `selectionSection` organize pickers independently of the table's existing grouped headings and CSV labels. Both menu and form variants use the same required-field rules, selected counts, partial states, descriptions and group/section toggles. Table menus preserve at least one visible field unless their existing caller explicitly permits an empty selection. Export-only choices do not mutate table visibility.

Contribution selections separate Identity, Pull requests, Reviews, approvals and merges (Merges performed joined Reviewer contributions and Approval contributions in P6, so each lens's set covers whole groups), Issues and Comment activity. Each authored/reviewed/approved volume group is split into Files and Lines. Contribution tables and Over time also pass `ColumnVisibility.sets`: the Columns menu then opens with a "Column set" radio group (Contributor, Reviewer, All credits, All columns) and its trigger reads "Columns · <set>" or "Columns · Custom" by `matchingColumnSet`; the CSV dialog shows the same choice as a "Column set" fieldset in place of its All columns button and changes only the export draft. Tables without sets keep "Columns". Repository summaries retain their existing domain groups; record and insight selectors use the same components with appropriate identity/status/date/activity groups. Borders separate groups, subsections and individual options; one bounded scroll surface avoids nested scrolling. This is selector organization only: metric definitions, row eligibility, table layouts, CSV headers and deferred-format scope are unchanged.

## Contribution export and measurement ordering

`TableValueColumn` is the pure value/sort contract shared by display columns and export selectors. `selectTableRows` filters and stably orders the full population before TanStack pagination or CSV projection. Contribution metric columns use coverage rank independent of direction: complete values, partial subtotals, then missing/not-applicable values. Numeric values sort within each rank; visible notes and CSV context state the policy. Other report columns keep their existing sort accessors and grouping behavior.

Both aggregate export layouts use `contributionCsv` through the same authenticated endpoint. The browser posts bounded JSON (64 KiB) so many selected columns do not inflate navigation URLs; the report-scope URL budget still applies to the scope itself. GET remains readable for existing export links. Missing company identity is invalid; an explicit empty identity means Unmapped company. Optional identity fields and metrics follow CSV choices, while stable IDs and report context remain automatic. The context columns include "Report lens" (`contributors` or `reviewers`) on aggregate, supporting-record and contribution Over time exports, and "Listed accounts" on overview exports ("Reviewer activity" for a Reviewers-lens overview without Show all, otherwise "All accounts with activity"). Over time supporting-record exports do not record the lens. Supporting-record exports retain their distinct row schema and share the generic serializer, filter/order and download lifecycle.

Account display logins preserve supplied casing; normalization is reserved for uniqueness and case-insensitive route keys. Human, Prebid agent, Bot and Unknown classification labels have one canonical definition; latest-activity roles remain separate. Account selection and CSV dialogs use the same bounded scroll frame with fixed header/actions.

## Preference cookies

Per-viewer preferences live in two cookies the server reads, so the first render is final: `dashboard-repositories` holds All repositories settings and sorts, record-list columns, charts and sorts per list kind, insight sorts, the repository and matrix Timeline presentation and their supporting-table sorts; `dashboard-contributions` holds the report scope shared by both lenses' overviews, Companies and their Timelines, columns and sort per lens and contribution table kind, Timeline presentation per lens, area and focus kind (`timeline.reviewers.<area>.<focus>` in the Reviewers lens), and the contribution supporting-table sort: 32 sections. `src/models/preferences.ts` lists every section. Sections are keyed by view kind and table kind, never by repository, account, company or sample.

- Both cookies use `Path=/`, a one-year `Max-Age`, `SameSite=Lax`, `Secure` on HTTPS, and no `HttpOnly`, because the client writes them through `document.cookie`. A browser matches `document.cookie` against the address the document was loaded at, not the one client navigation moved it to, so a `/repos`-only cookie would be unreadable to a report page reached by client navigation from another path.
- A value is base64url JSON carrying the format version, the account ID, the authentication revision and each section with its write sequence. A value for another version, account or revision is ignored, and a write for the current session replaces it. One browser therefore keeps one account's saved preferences at a time.
- The server validates each section through the existing readers before use. An invalid section renders the defaults, with a recovery notice where the view has a notice slot (All repositories settings, the contribution report scope, Timeline presentation and scope); after hydration the client deletes the section only while the cookie still holds that value. A Timeline presentation whose saved choices fail even on a bare entry is invalid on an entry that has to leave them out, with "Saved Timeline choices that do not fit this report were skipped."; a choice that fails only against an entry's explicit fields is left out of the redirect and stays saved. This and the one-time migration below are the only cookie writes after load, and neither writes history.
- Only deliberate changes write, each to its own section. All repositories settings, record-list presentation, contribution columns, the report scope and Timeline presentation merge the changed fields into the value the cookie holds, so another tab's fields survive; a contribution column change replaces only the columns its table renders. Relative presets stay presets.
- `name=value` stays within 3,072 bytes, and a longer value is read as malformed without being decoded. A write that would exceed it evicts the least recently updated other sections and shows "Saved preferences were full, so the least recently changed saved setting was removed."; a section that alone exceeds it is not saved and shows "This choice is too large to save. It applies to the current view only."
- Where a section had a localStorage value before the cookies, it is copied once into the absent section after validation, without evicting other sections, and applies from the next request. The localStorage keys are removed once copied, superseded by a cookie value or invalid.
- An entry is a report address holding only view selectors and return context, without `v`. The page helper (`src/server/canonical-page.ts`), called after `requireViewer()`, answers an entry whose saved view differs from the v1 defaults with a 307 to the saved explicit form: list routes take saved scope and presentation, detail routes presentation only (decision C2). A Timeline entry resolves its saved presentation as before, including leaving out a saved choice that does not fit. Drilldowns are never entries; the links that open record lists, insights, contribution tables and Timelines carry the viewer's saved presentation as explicit fields (decision C3). An old link answers with one 307 whose target already has the saved view applied.
- CSV export routes never read a preference cookie.
